= rclone_sync - structured backup workflow for rclone
:sectlinks:
:toc:

== overview

`rclone_sync` is a Makefile-driven wrapper around `rclone` that provides a
structured and repeatable workflow for data synchronization and backup.

It organizes execution into explicit phases, adds retry logic, logging,
statistics collection, reporting, optional email notifications and historical
tracking of executions.

Each run produces timestamped outputs (logs, stats, reports) organized in a
persistent directory structure, allowing historical tracking and inspection
over time. Convenient symlinks (`last`, `prev`, `status`) provide quick access
to recent executions.

The tool supports both batch execution (full pipeline) and interactive
inspection through dedicated targets (`status`, `status-v`, `history`).

Configuration is defined via Makefile variables and configuration files, and is
designed for system-level deployment.

The same tool can be reused across multiple projects through independent
configurations.

== features

* execution pipeline
** make-based workflow with explicit phases
** deterministic sequence: list -> run (start -> main -> end) -> report ->
   report-mail
** support for full pipeline or individual phase execution

* rclone integration
** data synchronization via `rclone`
** configurable synchronization rules and locations
** support for rule-specific options and filters

* execution control
** controlled execution within the run phase
** graceful stop support (`stop`)
** forced termination (`kill`)

* logging and observability
** global log file and per-rule logs
** structured execution tracing
** persistent logs across runs

* statistics and reporting
** per-run statistics collection
** per-rule metrics storage
** generation of log and summary reports

* historical data management
** timestamped storage of reports, stats, and usage
** directory structure organized by year/month
** persistent history of executions

* quick access helpers
** symlinks to recent data (`last`, `prev`)
** current status snapshot (`status`)
** fast access to latest reports and stats

* batch and rule execution
** support for multiple rules via configuration (`rules.list`)
** per-rule execution and tracking
** independent logs and stats per rule

* interactive inspection
** targets for runtime inspection (e.g. `status`, `status-v`, `history`)
** access to latest and historical execution data

* configuration model
** default configuration via `config.mk`
** site-specific overrides via `.include.mk`
** external configuration files (`rules.conf`, `rules.list`, `rclone.conf`)

* multi-instance deployment
** same tool reused across multiple projects with independent configuration

* notification
** optional email notification after execution

* portability
** minimal dependencies (make, shell, rclone)
** suitable for cron or system-level scheduling

== requirements / installation

=== requirements

- `make`
- `rclone`
- POSIX-compatible shell (`sh`, `bash`)
- optional: mail support for notifications

=== installation

Clone the repository:

[source,sh]
----
git clone <repo>
cd rclone_sync
----

Initialize local configuration:

[source,sh]
----
cp .include.mk.dist .include.mk
cp etc/rules.conf.dist etc/rules.conf
----

Edit `.include.mk` to override site-specific settings.

Configure `etc/rclone.conf` with the required remote provider settings.

Generate the active rules list:

[source,sh]
----
make list
----

Run a first synchronization:

[source,sh]
----
make run
----

== configuration

Configuration is split across Makefile variables and project-specific
configuration files.

Defaults values are defined in:

[source]
----
mk/config.mk
----

Project-specific settings are defined in:

[source]
----
.include.mk
----

Template configuration:

[source]
----
.include.mk.dist
----

`rclone_sync` also uses configuration files under `etc/`:

[source]
----
etc/
├── rclone.conf        # rclone backend configuration
├── rules.conf         # sync rule definitions
├── rules.conf.dist    # sync rules template
└── rules.list         # generated list of active rules
----

* `rclone.conf`
** standard rclone configuration
** contains provider-specific settings and credentials

=== configuration hierarchy

Configuration is evaluated in the following order:

[source]
----
mk/config.mk -> .include.mk -> etc/*.conf
----

* `config.mk`
** default values shared across all projects

* `.include.mk`
** project-specific overrides

* configuration files under `etc/`
** synchronization rules and runtime settings

=== template files

Files with the `.dist` suffix provide example configurations and templates.

Typical initialization:

[source,sh]
----
cp .include.mk.dist .include.mk
cp etc/rules.conf.dist etc/rules.conf
----

=== main variables

[source,make]
----
project      := $(shell basename "$(home)")
program_name := rclone_sync
version      := 2.0

rclone       := /usr/bin/rclone
sendmail     := /usr/sbin/sendmail

rclone_conf  := $(home)/etc/rclone.conf
rules_conf   := $(home)/etc/rules.conf
rules_list   := $(home)/etc/rules.list
----

=== sync rules

`rules.conf` defines synchronization behavior for individual rules.

Each rule can:

* be skipped
* define exclude patterns
* override the default rule identifier
* append additional rclone options

[source]
----
# format:
#     path
#         directive [value]

# directives:
#     skip              : skip this path
#     exclude <pattern> : exclude matching paths
#     ruleid <id>       : override rule identifier
#     opts <args>       : append raw rclone options
----

Example:

[source]
----
mordor
    skip

shire
    exclude *.orc

mithrandir
    ruleid gandalf

palantir
    opts --checksum
----

By default, each top-level directory under the source path generates one
synchronization rule.

Files stored directly under the source root are grouped into a special
`root-files` rule.

`rules.list` is generated from `rules.conf` and the source directory layout.
It is copied into each run metadata directory so that every run preserves the
exact list of rules used during execution.

== usage

=== pipeline execution

Typical scheduled execution:

[source,sh]
----
make list run report report-mail
----

=== core targets

* `list`
** generate the active `rules.list`

* `run`
** execute the synchronization pipeline: `start`, `main`, and `end`

* `report`
** generate the execution report

* `report-mail`
** send the generated report via email

=== control targets

* `stop`
** request a graceful stop (after current rule)

* `kill`
** send termination signals to the running shell, program and rclone processes

=== inspection targets

* `status`
** show current or last run status

* `status-v`
** show detailed per-rule status and execution statistics

* `history`
** list historical runs
** supports `from=<date>`, `to=<date>` and `n=<n>`

=== utility targets

* `help`
** show available targets and command syntax

* `dirs`
** create required directory structure

* `usage`
** collect usage snapshots

* `log-last`
** show latest execution log

=== notes

* most targets accept `runid=<runid>`, `runid=last` or `runid=prev`
* all targets operate on the current project configuration

== output

Runtime data is stored under `data/` and `log/`.

The output layout is timestamp-based and keeps historical data for reports,
statistics, and usage snapshots.

* reports
** stored under `data/reports/yyyy/yyyy.mm/`
** generated as both `.log` and `.txt` files
** exposed through `data/reports/last` and `data/reports/prev`

* statistics
** stored under `data/stats/yyyy/yyyy.mm/<runid>/`
** include one statistics file per rule
** include run metadata under `.meta/`
** exposed through `data/stats/last` and `data/stats/prev`

* status
** stored as run metadata under `.meta/status`
** exposed through `data/status`
** points to `data/stats/last/.meta/status`

* usage
** stored under `data/usage/yyyy/`
** exposed through `data/usage/last` and `data/usage/prev`

* logs
** main log stored under `log/<project>.log`
** per-rule logs stored under `log/run/<ruleid>.log`
** per-rule logs refer to the current run

`last` and `prev` symlinks provide stable access to the most recent and
previous outputs without requiring the caller to know the corresponding
`runid`.

== mail

Email notifications can be sent after report generation.

The `report-mail` target sends the generated report using the configured mail
delivery system.

Configuration is defined via Makefile variables:

[source,make]
----
mail_from := ...
mail_to   := ...
sendmail  := ...
----

The report is sent as plain text and corresponds to the output generated by the
`report` target.
